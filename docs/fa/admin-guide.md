# راهنمای مدیر سیستم و مهندس

جزئیات فنی هر بخش در [docs/backend.md](../backend.md) آمده است. شمارهٔ بخش مربوط داخل پرانتز نوشته شده است.

## ۱. کاربران و نقش‌ها (بخش ۲)

صفحهٔ «کاربران و نقش‌ها» فقط برای مدیر سیستم است.

* هر کاربر شخصی است. حساب مشترک برای شیفت نسازید، چون لاگ ممیزی باید نشان دهد چه کسی چه کرد.
* نقش را با کمترین دامنهٔ لازم بدهید، مثلاً «اپراتور» فقط برای `kish / pump_station`.
* کاربر جدید رمز موقت می‌گیرد و در اولین ورود باید آن را عوض کند.
* کاربری که می‌رود: «غیرفعال» کنید، حذف نکنید. با این کار نشست‌هایش فوراً بسته می‌شوند و سابقه‌اش باقی می‌ماند.
* آخرین مدیر سراسری فعال را نمی‌توان غیرفعال کرد یا نقشش را پایین آورد.
* ورود دومرحله‌ای برای نقش‌های `HUB_MFA_REQUIRED_ROLES` (توصیه: `admin,engineer`) اجباری است.

کارهای اضطراری از خط فرمان (روی سرور):

```
hub-admin unlock <user>            # باز کردن حساب قفل‌شده
hub-admin reset-password <user>    # رمز جدید (کاربر باید در ورود بعد عوضش کند)
hub-admin reset-mfa <user>         # گوشی گم شده
hub-admin create-admin --username <name>
hub-admin list-users
```

## ۲. پیکربندی

| چه چیز | کجا | اعمال |
|---|---|---|
| دستگاه‌ها و تگ‌ها | صفحهٔ «دستگاه‌ها» یا `config\devices\*.yaml` | از صفحه: بدون راه‌اندازی مجدد |
| حدود هشدار | «قواعد هشدار و کنترل» یا `config\alarms.yaml` | بدون راه‌اندازی مجدد |
| سیاست فرمان (`max_step`، اینترلاک، تأیید دونفره) | «قواعد هشدار و کنترل» یا `config\control.yaml` | بدون راه‌اندازی مجدد |
| اعلان‌ها | `config\notifications.yaml` | راه‌اندازی مجدد سرویس |
| رمزها و تنظیمات سرور | `‎.env` | راه‌اندازی مجدد سرویس |

پیش از هر تغییر دستی:

```
.venv\Scripts\python.exe -m hub.validate_config
```

هر تغییری که از صفحه انجام شود با نام کاربر در لاگ ممیزی ثبت می‌شود. پوشهٔ `config\` را در git نگه دارید.

## ۳. اعلان‌ها (بخش ۸)

* کانال‌ها: `email`، `telegram`، `sms` (هر درگاه HTTP)، `webhook`.
* قواعد تعیین می‌کنند کدام هشدار به کدام کانال برود: حداقل شدت، رخداد (وقوع یا رفع)، سایت، ناحیه، و هشدار آفلاین.
* برای هشدارهای سیستمی هاب یک قاعده با `min_severity: high` روی ایمیل یا تلگرام مدیر سیستم بگذارید.
* تست: `hub-admin notify-test [کانال]` یا دکمهٔ تست در صفحهٔ «سیستم». لاگ ارسال‌ها هم در همان صفحه است.

## ۴. سلامت هاب (بخش ۲۰)

صفحهٔ «سیستم»، بخش «سلامت هاب»، هر ۳۰ ثانیه بررسی می‌شود. هر مشکل به یک هشدار سیستمی تبدیل می‌شود:

| هشدار | معنی | اقدام |
|---|---|---|
| `system:database` | پایگاه داده پاسخ نمی‌دهد. داده‌ها در حافظه بافر می‌شوند | سرویس PostgreSQL، دیسک و اتصال را بررسی کنید |
| `system:disk:<درایو>` | فضای آزاد کمتر از ۱۰٪ (یا ۵٪ که حیاتی است) | پشتیبان‌ها و لاگ‌های قدیمی را منتقل کنید یا دیسک را بزرگ کنید |
| `system:backup` | پشتیبان شکست خورده، یا بیش از ۲۶ ساعت پشتیبانی نبوده | پوشهٔ پشتیبان، `pg_dump` و فضای دیسک را بررسی کنید |
| `system:restore` | تست بازیابی پشتیبان شکست خورده | فوری: آن پشتیبان قابل اعتماد نیست |
| `system:clock` | ساعت سرور بیش از ۳۰ ثانیه اختلاف دارد | `w32tm /resync` و تنظیمات NTP |
| `system:storage` | صف نوشتن در پایگاه داده پر شده | کندی پایگاه داده یا دیسک |
| `system:audit` | زنجیرهٔ لاگ ممیزی شکسته است | رخداد امنیتی: به واحد امنیت اطلاع دهید |
| `system:cert:<فایل>` | گواهی نزدیک انقضاست | گواهی را تمدید کنید |

## ۵. پشتیبان و بازیابی (بخش‌های ۶ و ۲۲)

* پشتیبان شبانه خودکار است و هر کدام بلافاصله آزمایش می‌شود. با `HUB_RESTORE_TEST=full`، هفته‌ای یک بار بازیابی کامل در یک پایگاه موقت انجام و بررسی می‌شود.
* پشتیبان دستی: `hub-admin backup --out <پوشه>`
* بررسی یک فایل: `hub-admin verify-backup <فایل> [--full]`
* بازیابی:

```
Stop-Service hub-api
.venv\Scripts\hub-admin.exe restore-backup <فایل> --yes
Start-Service hub-api
```

* `HUB_DATA_KEY` را جدا از سرور نگه دارید. بدون آن، پشتیبان‌های رمزشده خوانده نمی‌شوند.
* سالی دو بار بازیابی را روی یک سرور تست تمرین کنید.

## ۶. لاگ و ممیزی (بخش‌های ۱۳ و ۲۱)

* «لاگ ممیزی» (مهندس و مدیر): ورودها، تغییر کاربران، تأیید هشدارها، تغییرات پیکربندی و همهٔ فرمان‌ها با نتیجهٔ هر کدام. این لاگ قابل ویرایش یا حذف نیست.
* بررسی سلامت زنجیرهٔ ممیزی: `hub-admin verify-audit` (روزانه هم خودکار انجام می‌شود).
* فایل لاگ برنامه: `HUB_LOG_FILE`. با `HUB_LOG_FORMAT=json` برای سامانه‌های جمع‌آوری لاگ مناسب می‌شود. با `HUB_SYSLOG=udp://<siem>:514` همهٔ لاگ‌ها و یک نسخه از هر ردیف ممیزی به SIEM ارسال می‌شوند.
* شاخص‌ها برای Prometheus: `/metrics` با `HUB_METRICS_TOKEN`.

## ۷. ارتقا و بازگشت (بخش ۲۴)

```
.venv\Scripts\hub-admin.exe upgrade-check
powershell -ExecutionPolicy Bypass -File scripts\windows\upgrade.ps1 -Source D:\hub-<نسخه> [-Wheelhouse D:\wheels]
```

اسکریپت کارهای زیر را انجام می‌دهد:

۱. بررسی آمادگی
۲. پشتیبان‌گیری
۳. نصب نسخهٔ جدید
۴. اجرای آن و بررسی سلامت

اگر هر مرحله شکست بخورد، خودش به نسخهٔ قبل برمی‌گردد. `‎.env`، `config\`، `pki\`، `logs\` و `backups\` هرگز تغییر نمی‌کنند.
برای بازگشت دستی، از `rollback\<زمان>-<نسخه>\scripts\windows\rollback.ps1` استفاده کنید.
اگر نسخهٔ جدید پایگاه داده را تغییر داده باشد، داده‌های پس از ارتقا از دست می‌روند و اسکریپت این را اعلام می‌کند.

## ۸. کیفیت، امنیت و ظرفیت (فاز ۶)

* **پیش از هر تغییر در کد یا پیکربندی پایه:** `python scripts/check.py` را اجرا کنید. این فرمان همان بررسی‌های CI را اجرا می‌کند:
  * lint
  * اسکن امنیتی کد (bandit)
  * آسیب‌پذیری‌های شناخته‌شدهٔ وابستگی‌ها (pip-audit روی `requirements.lock`)
  * بررسی پیکربندی
  * همهٔ تست‌ها، از جمله ۳۰ آزمون نفوذ خودکار
* گزارش ارزیابی امنیتی و یافته‌ها: [docs/security-assessment.md](../security-assessment.md). پیش از بهره‌برداری، یک تست نفوذ مستقل هم لازم است (بخش ۶ همان سند).
* ظرفیت: [install.md](install.md) بخش ۱۲. اگر `validate_config` خطای «device connections» داد، یکی از این راه‌ها را انتخاب کنید:
  * گیت‌وی
  * لینوکس (Docker)
  * تقسیم دستگاه‌ها بین دو هاب
* مستندات تعاملی API (`/api/docs`) در بهره‌برداری خاموش است. فقط برای توسعه آن را با `HUB_API_DOCS=true` روشن کنید.

## ۹. ورود با حساب سازمانی (Active Directory)

با این قابلیت کارکنان با همان نام کاربری و رمز ویندوز خود وارد هاب می‌شوند (جزئیات فنی: بخش ۲۷ فایل backend.md).

**راه‌اندازی (با واحد IT):**

1. یک حساب سرویس فقط‌خواندنی در Active Directory بسازید، مثلاً `svc-hub`.
2. برای نقش‌ها گروه بسازید، مثلاً `Hub-Admins`، `Hub-Engineers`، `Hub-Operators-Substation` و `Hub-Viewers`، و کارکنان را عضو کنید.
3. فایل `config\ldap.example.yaml` را به `config\ldap.yaml` کپی کنید و این‌ها را تنظیم کنید:
   * آدرس کنترلر دامنه، با `ldaps://` یا `ldap://` همراه `start_tls`
   * حساب سرویس
   * محل کاربران و گروه‌ها
   * جدول «گروه ← نقش»
4. در `‎.env` این‌ها را بگذارید:
   * `HUB_LDAP_BIND_PASSWORD`: رمز حساب سرویس
   * `HUB_LDAP_CA_FILE`: مسیر گواهی CA سازمان
5. `python -m hub.validate_config` را اجرا کنید، بعد پیکربندی را دوباره بارگذاری کنید یا سرویس را راه‌اندازی مجدد کنید.

**نکات مهم:**

* اتصال بدون رمزنگاری پذیرفته نمی‌شود، چون رمز کاربران روی شبکه آشکار می‌رفت.
* کسی که عضو هیچ گروه تعریف‌شده‌ای نیست، وارد نمی‌شود.
* نقش‌ها در هر ورود از گروه‌های دایرکتوری گرفته می‌شوند. برای تغییر نقش یک نفر، عضویت گروهی او را در Active Directory عوض کنید، نه در صفحهٔ «کاربران و نقش‌ها».
* رمز کاربران دایرکتوری فقط در Active Directory عوض می‌شود.
* قفل شدن پس از رمز اشتباه، غیرفعال کردن در هاب، ورود دومرحله‌ای و لاگ ممیزی برای این کاربران هم کار می‌کند.
* **دست‌کم یک مدیر محلی نگه دارید** (همان که با `hub-admin create-admin` ساخته شد). اگر کنترلر دامنه در دسترس نباشد، فقط حساب‌های محلی می‌توانند وارد شوند.

## ۱۰. عیب‌یابی

| مشکل | بررسی |
|---|---|
| داشبورد باز نمی‌شود | `Get-Service hub-api`، فایروال، `/api/health`، فایل لاگ |
| `/api/health` می‌گوید `degraded` | پایگاه داده قطع است؛ داده‌ها بافر می‌شوند |
| دستگاه آفلاین | «آخرین خطا» در صفحهٔ دستگاه، `hub-commission read <id>`، و `Test-NetConnection` |
| مقدار عجیب | `hub-commission modbus-probe` / `s7-dump` با `--expect` ([commissioning.md](commissioning.md)) |
| فرمان `rejected_disabled` | `HUB_CONTROL_ENABLED`، فعال بودن دستگاه، `access: read_write` روی تگ |
| فرمان `unverified` | ضریب یا ترتیب word، یا دستگاه در حالت Local است |
| حساب قفل شد | `hub-admin unlock <user>` |
| پیام اعلان نمی‌رسد | `hub-admin notify-test`، لاگ اعلان‌ها در صفحهٔ «سیستم» |
| سرویس پس از ارتقا بالا نمی‌آید | لاگ؛ پیام «refusing to start» یعنی پایگاه داده از نسخهٔ جدیدتری است و باید بازگشت انجام شود |
