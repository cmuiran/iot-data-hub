## ۲. نتایج آزمون (اجرای واقعی)

| | نتیجه |
|---|---|
| کل پروژه (اجرای آخر، پیش از دو اصلاح پایانی) | **۹۴۱ موفق، ۳ ناموفق، ۲ ردشده** (۱۳ دقیقه و نیم) |
| پس از اصلاح، آزمون‌های همان سه فایل | ۴۰ موفق، ۱ ناموفق (`test_skill_docs`) |
| ruff روی `hub`، `backend`، `tests`، `simulators` | بدون خطا |
| bandit روی `hub`، `backend`، `simulators` | ۰ یافتهٔ متوسط یا شدید |

**سه آزمون ناموفق:**
* دو آزمون سلامت (`test_all_ok_on_a_healthy_hub`، `test_alarm_list_and_ack`): درایو C این سیستم
  ۹۲٪ پر است و Hub درست هشدار «کمبود دیسک» می‌داد. آزمون نباید به دیسک توسعه‌دهنده وابسته باشد؛
  آستانهٔ دیسک در تنظیمات آزمون پایین آمد (آزمون خود دیسک آستانه‌های خودش را دارد) و هر دو موفق‌اند.
* `test_skill_docs`: از پیش از این فازها خراب است (نمونهٔ FINS، MC، EtherNet/IP و IEC 104 در
  راهنمای مهارت add-device نیست). طبق دستور قبلی شما آن محتوا نوشته نشد.

## ۳. آزمون بار (`simulators/platform_loadtest.py`، روی همین لپ‌تاپ ویندوز)

| | نتیجه |
|---|---|
| ثبت ۱۰٬۰۰۰ دستگاه | ۵٫۰ ثانیه |
| برچسب و اعتبارنامهٔ ۱۰٬۰۰۰ دستگاه | ۲٫۰ ثانیه |
| روشن کردن ۳۰۰ دستگاه | ۲٫۶ ثانیه (پیش از اصلاح: ۳۰۹ ثانیه) |
| ۳۰۰ دستگاه، هر کدام یک پیام در ثانیه، ۴۵ ثانیه | **۲۰۴ درخواست در ثانیه، بدون خطا**؛ تأخیر میانه ۵۷۷ ms، p95 ۲٫۵ s، p99 ۴٫۱ s |
| نمونه‌ها | ۴۰٬۲۹۶ دریافت = ۴۰٬۲۹۶ ذخیره، هیچ نمونه‌ای از دست نرفت |
| حافظه / CPU فرایند Hub | ۱۲۸ MB / ۶۷٪ یک هسته |

**یافته‌ها و اصلاح‌ها:**
* با هر روشن/خاموش شدن یک دستگاه کل جدول Tagها خوانده می‌شد (با ۱۰٬۰۰۰ دستگاه = ۷۰٬۰۰۰ سطر)؛
  اکنون فقط Tagهای همان دستگاه. نتیجه: ۱۱۷ برابر سریع‌تر.
* در اولین اندازه‌گیری، کلاینت آزمون در همان فرایند Hub بود و خودش گلوگاه شد؛ دستگاه‌های شبیه‌سازی
  به فرایندهای جدا رفتند تا فقط Hub اندازه گرفته شود.
* سقف حدود ۲۰۰ درخواست در ثانیه به تعداد اتصال وابسته نیست (با ۴۰ و ۲۰۰ اتصال یکسان بود)؛ هزینهٔ
  هر درخواست روی ویندوز حدود ۳ ms است. استقرار هدف لینوکس است و برای بار بیشتر چند نمونهٔ hub
  پشت توزیع‌کنندهٔ بار (HA) یا MQTT با اشتراک مشترک. **آزمون بار روی لینوکس و EMQX انجام نشده است.**

## ۵. استقرار ابری

فایل‌ها در `deploy/` و راهنما در [deploy-cloud.md](deploy-cloud.md). Docker روی این سیستم نصب
نیست، پس **پیکربندی اجرا نشده** است؛ فقط معتبر بودن YAML آن بررسی شد. پیش از استفادهٔ واقعی روی یک
سرور آزمایشی اجرا شود.

## ۶. مسائل باقی‌مانده

1. پیام‌های لحظه‌ای برای اپ مشتری (فعلاً هر ۵ ثانیه تازه می‌شود)، اعلان Push، نمودار تاریخچه در اپ.
2. ماشهٔ طلوع/غروب، ویرایش اتوماسیون در اپ (فعلاً حذف و ساخت دوباره)، شرط و چند اقدام در سازندهٔ اپ.
3. تعطیلات قمری هر سال باید به‌صورت تاریخ افزوده شوند (محاسبه نمی‌شوند).
4. حافظهٔ اولویت اتوماسیون‌ها برای هر گره جداست؛ در چند گره هم‌زمان این قاعده سراسری نیست.
5. Firmware امضاشده توسط Hub، rollout درصدی، امکان تعویق به‌روزرسانی توسط مالک.
6. ارتباط هاب لبه با مرکز (مسیر لبه ← مرکز) و دریافت SNMP Trap.
7. آزمون بار روی لینوکس، آزمون واقعی docker-compose، EMQX واقعی با hookها.
8. پیام خطای «شناسه قبلاً ثبت شده» برای سازندگان (یکتایی سراسری لازم است؛ بازبینی).
9. CI روی GitHub فعال نیست.
10. فضای درایو C توسعه (۸٪ آزاد).
