# روال راه‌اندازی میدانی (Commissioning) و تست پذیرش سایت (SAT)

راه‌اندازی هر دستگاه به همین ترتیب انجام می‌شود. تا وقتی تست فرمان انجام نشده، فرمان از راه دور خاموش می‌ماند (`HUB_CONTROL_ENABLED=false`).

```
اطلاعات دستگاه ─► تست شبکه ─► کاوش با hub-commission ─► ثبت دستگاه ─► validate_config
     ─► تست خواندن و مقایسه با نمایشگر ─► هشدارها ─► (در صورت نیاز) تست فرمان ─► اعلان‌ها ─► SAT
```

`hub-commission` فقط می‌خواند و هیچ مقداری روی دستگاه نمی‌نویسد. نوشتن فقط از لایهٔ ایمنی هاب انجام می‌شود (بخش ۷).

همهٔ فرمان‌ها از پوشهٔ برنامه اجرا می‌شوند. رمز دستگاه‌ها از `‎.env` خوانده می‌شود.
اگر رمزها در فایل دیگری هستند، از `--env-file <فایل>` استفاده کنید.

---

## ۱. اطلاعات لازم برای هر دستگاه

| پروتکل | اطلاعات |
|---|---|
| Modbus TCP / RTU | IP و پورت (یا پورت COM، baud، parity)، unit id، جدول رجیستر (آدرس، نوع، ضریب، واحد)، اینکه شماره‌گذاری datasheet از ۰ است یا ۱، ترتیب word برای مقادیر ۳۲ بیتی |
| OPC UA | آدرس endpoint، سیاست امنیتی، نام کاربری (اگر دارد)، فهرست NodeId یا مسیر پوشه‌ها |
| MQTT | broker، پورت، TLS، نام کاربری، topic تله‌متری، نمونهٔ payload |
| Siemens S7 | IP، rack/slot، شمارهٔ DB و آفست‌ها. در S7-1200/1500 گزینهٔ PUT/GET باید فعال و «optimized block access» آن DB خاموش باشد |
| HTTP/REST | آدرس پایه، مسیرها، نوع احراز هویت، نمونهٔ پاسخ JSON |
| SNMP | IP، نسخه (v2c/v3)، community یا کاربر v3، OIDها (مثلاً UPS-MIB) |

نام‌گذاری تگ‌ها: `<site>.<area>.<device_id>.<tag>` با حروف کوچک انگلیسی و `_`، مثلاً
`kish.pump_station.plc_01.motor_speed`. `device_id` در کل سیستم یکتاست.

## ۲. تست شبکه

```
ping <IP>
Test-NetConnection <IP> -Port 502      # 102 برای S7، 4840 برای OPC UA، 1883/8883 برای MQTT
```

پورت بسته یعنی مشکل فایروال، VLAN یا خاموش بودن سرویس روی دستگاه است. پیش از ادامه آن را حل کنید.
برای SNMP (UDP) این تست کاربرد ندارد؛ مستقیم از `snmp-walk` استفاده کنید.

## ۳. کاوش دستگاه با hub-commission

### Modbus

پیدا کردن unit idهای پاسخ‌دهنده (مخصوصاً پشت گیت‌وی RS-485):

```
hub-commission modbus-scan --host 10.0.0.9 --units 1-32
```

مقایسهٔ یک مقدار با نمایشگر دستگاه. فرض کنید نمایشگر ولتاژ را 230.4 نشان می‌دهد و datasheet می‌گوید «30101: Voltage L1, float»:

```
hub-commission modbus-probe --host 10.0.0.5 --unit 1 --ref 30101 --count 4 --expect 230.4
```

خروجی همهٔ تفسیرهای ممکن را چاپ می‌کند (uint16/int16، float32/int32/uint32 و float64 در چهار ترتیب byte/word).
علامت `*` رجیستر قبل از آدرس را نشان می‌دهد؛ اگر datasheet شماره‌گذاری را از ۱ شروع کرده باشد، جواب درست همان است.
با `--expect` تفسیرهایی که با مقدار نمایشگر می‌خوانند (با ضریب ۱۰ به توان n) پیدا و یک تگ پیشنهادی چاپ می‌شود.
`byte_order` و `word_order` روی `connection` دستگاه تنظیم می‌شوند، نه روی تگ.

| نشانه | علت محتمل | راه‌حل |
|---|---|---|
| عدد بسیار بزرگ یا بسیار کوچک (مثل ‎3.6e+24) | ترتیب word یا byte اشتباه | `word_order: little` (رایج‌ترین حالت) یا `byte_order` |
| مقدار ۱۰، ۱۰۰ یا ۱۰۰۰ برابر | ضریب | `scale: 0.1` / `0.01` |
| مقدار تگ کناری را نشان می‌دهد | آدرس یکی جابه‌جا | آدرس منهای ۱ (datasheet از ۱ شمرده) |
| `exception 2 (illegal data address)` | آدرس یا نوع رجیستر (holding/input) اشتباه، یا `--count` بزرگ | نوع دیگر رجیستر را امتحان کنید |
| `no answer` | IP، unit id، فایروال، یا master دیگری اتصال تنها را گرفته | `modbus-scan`، قطع master دیگر |
| `exception 11 (gateway target did not respond)` | گیت‌وی پاسخ می‌دهد ولی دستگاه پشت آن نه | سیم‌کشی RS-485، baud، unit id |

### OPC UA

```
hub-commission opcua-browse --endpoint opc.tcp://10.0.0.7:4840 --depth 4 --yaml
hub-commission opcua-browse --device plc_01 --yaml        # با امنیت و کاربر تعریف‌شده برای دستگاه
```

همهٔ متغیرها را با NodeId، نوع داده، مقدار و دسترسی (`r` یا `rw`) فهرست می‌کند. با `--yaml` تگ پیشنهادی هم چاپ می‌شود.
اگر سرور فقط اتصال امن می‌پذیرد، ابتدا دستگاه را با گواهی ثبت کنید (`hub-admin make-cert`) و از `--device` استفاده کنید.
گواهی کلاینت هاب باید در سرور «trusted» شود.

### MQTT

```
hub-commission mqtt-listen --broker plant_broker --topic "kish/#" --seconds 20 --yaml
```

topicها، تعداد پیام‌ها، نرخ پیام و همهٔ فیلدهای JSON را با مسیر (`$.data.temp`) نشان می‌دهد.
اگر پیامی نیامد، به این‌ها دقت کنید: حروف کوچک و بزرگ topic، ACL حساب broker، و اینکه برخی دستگاه‌ها فقط هنگام تغییر مقدار پیام می‌فرستند.

### Siemens S7

```
hub-commission s7-dump --host 10.0.0.8 --rack 0 --slot 1 --db 1 --start 0 --size 32 --expect 41.5
```

یک dump هگز چاپ می‌کند و جدولی از INT، WORD، DINT و REAL در هر آفست.
با `--expect` آدرس پیشنهادی را هم می‌دهد، مثل `DB1.DBD4 float32`.
rack/slot معمول: S7-1200/1500 = 0/1، S7-300 = 0/2.

### HTTP/REST

```
hub-commission http-get --url http://10.0.0.30/api/v1/status --yaml
hub-commission http-get --device inverter_01 --yaml        # همهٔ مسیرهای تگ‌های دستگاه، با احراز هویت آن
```

### SNMP

```
hub-commission snmp-walk --host 10.0.0.20 --community-env HUB_UPS01_COMMUNITY --oid 1.3.6.1.2.1.33 --yaml
```

community از متغیر محیطی خوانده می‌شود و هرگز در خط فرمان نوشته نمی‌شود. برای SNMP v3 دستگاه را ثبت کنید و از `--device` استفاده کنید.

## ۴. ثبت دستگاه

سه راه دارید:

* **مهارت add-device در Claude Code** (توصیه‌شده): datasheet، جدول رجیستر، خروجی `--yaml` بالا یا ردیف Excel را بدهید.
  فایل `config/devices/<device_id>.yaml` ساخته و بررسی می‌شود. برای ثبت گروهی از `devices.xlsx` هم استفاده می‌شود.
* **صفحهٔ «دستگاه‌ها»** در داشبورد (نقش مهندس): ساخت از الگو، ویرایش، اعتبارسنجی و اعمال بدون راه‌اندازی مجدد.
* **ویرایش دستی YAML** و سپس بررسی:

```
.venv\Scripts\python.exe -m hub.validate_config
```

پیش‌فرض همهٔ تگ‌ها فقط‌خواندنی است. `access: read_write` را فقط در بخش ۷ و همراه با `min`/`max` اضافه کنید.
اگر می‌خواهید دستگاه را پیش از اعلام به اپراتورها تست کنید، `enabled: false` بگذارید؛ `hub-commission read` دستگاه غیرفعال را هم می‌خواند.

## ۵. تست خواندن و مقایسه با نمایشگر

```
hub-commission read meter_01 --seconds 60 --out sat\meter_01.md
```

همهٔ تگ‌ها با درایور واقعی هاب خوانده می‌شوند. برای هر تگ این‌ها گزارش می‌شود: مقدار، کیفیت (quality)، تعداد به‌روزرسانی، کمینه و بیشینه در مدت تست، و راهنمایی برای موارد مشکوک.
کد خروج ۰ یعنی همه سالم‌اند.
فایل `.md` فرم SAT همان دستگاه است و ستون «Verified on site» را در محل تیک می‌زنید. با پسوند `.json` خروجی ماشینی می‌گیرید.

برای هر تگ دست‌کم سه بار با نمایشگر یا مرجع محلی مقایسه کنید: در حالت عادی، در یک نقطهٔ کار دیگر (مثلاً بار بیشتر یا پمپ روشن و خاموش)، و برای تگ‌های دودویی در هر دو حالت.
اختلاف قابل‌قبول: ‎±۱٪‏ یا دقت نمایشگر (هر کدام بیشتر است).

## ۶. هشدارها

* حدود هشدار (`config/alarms.yaml` یا صفحهٔ «قواعد هشدار و کنترل») را با بهره‌بردار توافق کنید.
* هر هشدار حیاتی را یک بار واقعاً تست کنید. اگر ایمن است، حالت را در دستگاه ایجاد کنید؛ وگرنه حد را موقتاً تغییر دهید و بعد برگردانید (این تغییر در لاگ ممیزی ثبت می‌شود).
* در صفحهٔ «هشدارها» بررسی کنید: هشدار ظاهر شد، صدای هشدار پخش شد، تأیید (ack) کار کرد، و هشدار پس از برطرف شدن پاک شد.

## ۷. تست فرمان از راه دور (با احتیاط کامل)

فقط برای تگ‌هایی که بهره‌بردار رسماً خواسته است. **بدون مجوز کار (permit) و حضور اپراتور کنار دستگاه انجام نشود.**

### پیش‌شرط‌ها

* ☐ مجوز کار صادر شده و اپراتور محلی با بی‌سیم یا تلفن در ارتباط است.
* ☐ کلید Local/Remote دستگاه در حالت مجاز است و توقف اضطراری محلی در دسترس است.
* ☐ مقدار «امن» برای تست و مقدار فعلی (برای برگرداندن) یادداشت شده است.
* ☐ در فایل دستگاه، تگ `access: read_write` با `min` و `max` محافظه‌کارانه دارد.
* ☐ در `config/control.yaml` این‌ها تعیین شده: `max_step`، `min_interval_s`، اینترلاک‌ها، و `confirm: true` برای فرمان‌های حساس.
* ☐ فقط نقش‌های لازم `tag.write` دارند (اپراتور و بالاتر، و فقط در site/area خودشان).
* ☐ `python -m hub.validate_config` بدون خطاست.

### روشن کردن

در `‎.env` مقدار `HUB_CONTROL_ENABLED=true` را بگذارید و سرویس را دوباره راه بیندازید (`Restart-Service hub-api`).

### ترتیب تست (هر مرحله در فرم ثبت شود)

| # | اقدام | نتیجهٔ مورد انتظار |
|---|---|---|
| 1 | کاربر «بیننده» فرمان بدهد | دکمهٔ فرمان دیده نمی‌شود، یا خطای دسترسی |
| 2 | مقدار بیرون از `min`/`max` | `rejected_range` و چیزی به دستگاه فرستاده نمی‌شود |
| 3 | تغییر بزرگ‌تر از `max_step` | `rejected_range` |
| 4 | دو فرمان پشت هم سریع‌تر از `min_interval_s` | فرمان دوم `rejected_rate` |
| 5 | حالت اینترلاک فعال (اگر تعریف شده) | `rejected_interlock` |
| 6 | تغییر کوچک و امن | `applied`؛ مقدار بازخوانی‌شده برابر است و اپراتور محلی تغییر را تأیید می‌کند |
| 7 | تگ با `confirm: true` | فرمان منتظر می‌ماند؛ همان کاربر نمی‌تواند تأیید کند؛ کاربر دوم (مهندس) تأیید می‌کند و فرمان `applied` می‌شود |
| 8 | برگرداندن مقدار اولیه | `applied` |
| 9 | صفحهٔ «لاگ ممیزی» | همهٔ تلاش‌ها با کاربر، مقدار قبلی و جدید، دلیل و نتیجه ثبت شده‌اند |

اگر نتیجه `unverified` (مقدار بازخوانی‌شده متفاوت) یا `timeout` بود، تست را متوقف کنید.
اول وضعیت دستگاه را محلی بررسی کنید؛ بعد ضریب، ترتیب word و آدرس را دوباره کنترل کنید.

### پس از تست

بهره‌بردار تصمیم می‌گیرد که فرمان از راه دور روشن بماند یا نه. اگر نه، `HUB_CONTROL_ENABLED=false` را برگردانید و سرویس را دوباره راه بیندازید. تصمیم را در گزارش ثبت کنید.

## ۸. اعلان‌ها (ایمیل، تلگرام، پیامک)

```
.venv\Scripts\hub-admin.exe notify-test                 # همهٔ کانال‌های config\notifications.yaml
.venv\Scripts\hub-admin.exe notify-test ops_telegram    # یک کانال
```

این فرمان پایگاه داده لازم ندارد. برای هر کانال `sent` یا `FAILED` همراه با علت چاپ می‌کند.
`sent` یعنی سرور پیام را پذیرفته است؛ رسیدن پیام را روی گوشی یا صندوق گیرنده بررسی کنید.
از داشبورد هم صفحهٔ «سیستم»، بخش اعلان‌ها، دکمهٔ تست دارد. پس از آن یک هشدار واقعی (بخش ۶) را تا رسیدن پیام دنبال کنید.

| خطا | علت |
|---|---|
| `environment variable ... is not set` | رمز یا توکن در `‎.env` نیست |
| `telegram answered 401` | توکن ربات اشتباه است |
| `telegram answered 400 chat not found` | ربات به گروه اضافه نشده یا chat id اشتباه است |
| خطای SMTP مربوط به auth یا TLS | کاربر یا رمز، پورت 587 با `starttls` یا 465 با `ssl` |
| `SMS gateway answered 4xx` | کلید API، قالب پارامترها یا اعتبار حساب پیامک |

## ۹. چک‌لیست تست پذیرش سایت (SAT)

| # | مورد | نتیجه |
|---|---|---|
| 1 | `hub-commission read` همهٔ دستگاه‌ها در ۱۰ دقیقه: همه `OK` | ☐ |
| 2 | مقایسهٔ هر تگ با نمایشگر محلی (بخش ۵) | ☐ |
| 3 | قطع کابل شبکهٔ یک دستگاه: وضعیت `offline`، هشدار ارتباط، و بازگشت خودکار پس از وصل | ☐ |
| 4 | خاموش و روشن کردن سرور: سرویس خودکار بالا می‌آید و داده‌ها ادامه می‌یابند | ☐ |
| 5 | قطع پایگاه داده (توقف سرویس PostgreSQL به مدت ۲ دقیقه): هشدار `system:database`؛ پس از وصل، داده‌های بافرشده ذخیره می‌شوند | ☐ |
| 6 | هشدارهای حیاتی: ظاهر شدن، صدا، تأیید، پاک شدن (بخش ۶) | ☐ |
| 7 | اعلان‌ها روی همهٔ کانال‌ها رسیدند (بخش ۸) | ☐ |
| 8 | روند (trend) و گزارش یک روز گذشته درست است؛ خروجی Excel/CSV باز می‌شود | ☐ |
| 9 | نقش‌ها: بیننده فقط می‌بیند؛ اپراتور فقط در area خود فرمان می‌دهد؛ مهندس پیکربندی می‌کند | ☐ |
| 10 | تست فرمان طبق بخش ۷ (اگر در محدودهٔ پروژه است) | ☐ |

| 12 | HTTPS بدون هشدار مرورگر در رایانه‌های اپراتور | ☐ |
| 13 | پشتیبان شبانه گرفته شد و تست بازیابی آن `ok` بود (صفحهٔ «سیستم») | ☐ |
| 14 | `hub-admin verify-audit`: هر دو زنجیره OK | ☐ |
| 15 | ساعت سرور همگام است (هشدار `system:clock` نیست) | ☐ |
| 16 | `hub-admin upgrade-check`: ready | ☐ |
| 17 | رابط فارسی (RTL) و انگلیسی، تقویم شمسی در گزارش‌ها | ☐ |
| 18 | آموزش اپراتورها انجام شد ([training.md](training.md)) | ☐ |
